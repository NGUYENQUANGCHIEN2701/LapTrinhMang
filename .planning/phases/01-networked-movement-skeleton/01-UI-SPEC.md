# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope Note

This phase renders a live, two-tank arena view only (COMBAT-01). There is no login, no menu, no
HUD (no HP bars, no minimap, no chat, no leaderboard) — those arrive in Phases 2-5. The entire
visible surface is: a page heading, a one-line connection/match status, and an 800x600 Canvas
arena showing two tanks moving in real time. This contract is scoped accordingly; it does not
invent UI for features that don't exist yet.

---

## shadcn Gate Decision

`components.json` not found (greenfield, no `client/` scaffolded yet). Tech stack is Vite + React
per RESEARCH.md, so the gate applies — but this phase's entire UI surface is a `<canvas>` element
plus one heading and one status line: **zero forms, zero buttons, zero cards, zero navigation**.
Movement is keyboard-driven (no on-screen controls); connection happens automatically on page
load (no click-triggered action). A component library has nothing to do this phase.

**Decision: Tool: none for Phase 1.** Revisit shadcn initialization when Phase 3 introduces the
win/loss result screen (LIFE-02) or Phase 4 introduces auth forms (AUTH-01/02) — both need real
interactive components (buttons, cards, inputs) that justify the investment.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#18181b` (near-black slate) | Page background outside the arena canvas |
| Secondary (30%) | `#27272a` (dark neutral gray) | Arena/canvas surface fill (the "floor" tanks move on) — flat, no grid/texture (art placeholder per CONTEXT.md) |
| Accent (10%) | `#22c55e` (green) | Reserved for: (1) the "Connected" status-line text color, (2) the local player's own-tank identification ring (see Game Rendering Contract) |
| Destructive | `#ef4444` (red) | Reserved for: the "Connection lost" error status-line text color only. No destructive buttons/actions exist this phase. |

Accent reserved for: connection-status "connected" text, local-player own-tank ring. Never applied
to page chrome decoratively, never applied to the opponent's tank.

### Game Entity Colors (canvas content — not part of the 60/30/10 chrome split)

Tank fill colors are gameplay-identity colors, distinct from the page's UI accent system:

| Role | Value | Usage |
|------|-------|-------|
| Player 1 tank | `#3b82f6` (blue) | Fill color for the tank assigned `playerId: "P1"` |
| Player 2 tank | `#f97316` (orange) | Fill color for the tank assigned `playerId: "P2"` |
| Tank border | 20%-darker shade of the tank's own fill color | 2px stroke around the tank body for definition against the arena background |
| Barrel/turret indicator | `#3f3f46` (neutral dark gray) | Same for both tanks — the facing indicator itself is not player-colored, only the body is |

Blue/orange is a high-contrast, colorblind-considerate pairing so the two tanks stay
distinguishable independent of the accent-ring own-tank indicator.

## Game Rendering Contract

*(Phase-specific addition — this phase's actual visual contract lives here, not just in the
generic sections above. Adopted from RESEARCH.md's Open Question 1 recommendation so planner and
executor share one canonical set of numbers instead of inventing them independently.)*

### Arena

| Property | Value |
|----------|-------|
| Canvas size | 800x600px, fixed — no camera scroll/zoom/follow (D-05) |
| Background fill | Secondary color `#27272a`, flat, no grid/texture |
| Frame | 3px solid `#52525b` border around the canvas edge — pure visual boundary marker (tanks are already clamped inside via server-side bounds; the frame is not gameplay logic) |
| Walls/obstacles | None rendered this phase — COMBAT-05 is Phase 2 scope |

### Tank Visual Spec

| Property | Value |
|----------|-------|
| Bounding box | 32x32px square |
| Body shape | Rectangle, 28x20px (in "facing up" orientation), 2px corner radius, centered in the bounding box |
| Body fill | Player color (`#3b82f6` P1 / `#f97316` P2) with a 2px border in a 20%-darker shade of the same color |
| Barrel/turret | Rectangle, 6x14px, fill `#3f3f46`, protruding from the body's front-center edge by ~10px in the current facing direction |
| Rotation | Body + barrel rotate as one rigid unit (`ctx.translate` + `ctx.rotate` around the tank's center). Angle mapping: UP = 0°, RIGHT = 90°, DOWN = 180°, LEFT = 270°. Rotation **snaps instantly** on facing change — no tween/interpolation this phase (smooth rotation animation is future polish, out of scope per CONTEXT.md D-01/D-02, 4-directional only) |
| Movement rendering | Position drawn directly from the last server-broadcast `{x, y}` every `requestAnimationFrame` tick — no client-side prediction/interpolation this phase (per RESEARCH.md ARCHITECTURE.md Pattern 2/4) |
| Own-tank indicator | 2px accent-green (`#22c55e`) ring drawn 4px outside the local player's own tank bounding box only — lets a player instantly identify "which tank is mine" without translating color→role. Never drawn around the opponent's tank. |
| Effects | None — flat fill only, no shadows/gradients/textures/particles (simple-shapes placeholder per CONTEXT.md; muzzle flash/explosions are POLISH-04, v2/out of scope) |

### Spawn Coordinates (adopted from RESEARCH.md recommendation)

| Player | Spawn position | Initial facing |
|--------|-----------------|-----------------|
| P1 | (40, 40) — top-left corner, inset so the 32px tank stays fully on-screen | DOWN |
| P2 | (728, 528) — bottom-right corner, same inset | UP |

Matches D-06 (opposite corners). Tank speed: ~150px/sec (Claude's discretion per D-04; tunable
constant isolated in one config location per RESEARCH.md, not scattered magic numbers).

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Not applicable — connection happens automatically on page load (WebSocket opens immediately, no click-to-connect step); movement is keyboard-driven (WASD/arrow keys), so there is no click-triggered action anywhere in this phase. |
| Loading state | "Connecting…" — shown before the first server `joined` message arrives |
| Empty state heading | "Waiting for opponent…" — shown once the local client has joined but the second player has not yet connected |
| Empty state body | "You're connected as Player {N}. The match starts as soon as a second player opens this page." |
| Connected (both players) status | "Match live — you are Player {N} ({color})." — shown once both `P1` and `P2` have joined and the tick loop is broadcasting state |
| Error state | "Connection lost — check that the server is running, then refresh this page to reconnect." — shown on WebSocket `onclose`/`onerror` |
| Destructive confirmation | Not applicable — no destructive actions exist this phase (leave-match/forfeit confirmation arrives with LIFE-01/LIFE-02 in Phase 3). |

Status line color mapping: default/loading = neutral `#a1a1aa` (muted gray, not yet declared as a
token above — add as needed), connected = accent `#22c55e`, error = destructive `#ef4444`.

**Elements classified:**
- `arena-canvas` — 800x600 Canvas rendering the game arena and both tanks — kinds: `media`, `list-collection` (authored override, confirmed against the researcher's own classification — probe's auto-classifier initially returned `unclassified` on this element's prose)
- `tank-entities` — the 1-2 tank sprites drawn on the canvas (local + opponent, opponent appears once connected) — kind: `list-collection` (auto-detected)
- `connection-status` — one-line status text above the canvas — kind: `static-content` (auto-detected)

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | arena-canvas (media, list-collection) | ✅ covered | Only the local player's tank renders until the opponent's `joined` message arrives; the opponent's spawn corner stays visually empty (no placeholder tank drawn) — ties to the "Waiting for opponent…" empty-state copy row above. |
| loading | arena-canvas (media, list-collection) | ✅ covered | Canvas renders the empty arena background (no tanks) while the status line reads "Connecting…", before the first server `joined`/`state` message is received. |
| error | arena-canvas (media, list-collection) | ✅ covered | On WS `onclose`/`onerror`, status line switches to destructive-red "Connection lost" copy; canvas freezes on the last-received state rather than clearing, keeping the frozen moment visible for context. |
| populated | arena-canvas (media, list-collection) | ✅ covered | Happy path fully specified in Game Rendering Contract: both tanks render at last-known server position every ~30Hz tick, rotating in place to match `facing`. |
| partial | arena-canvas (list-collection) | dismissed | Each tick's tank record (`x, y, facing`) is atomic — the server never broadcasts a partially-filled tank state, so the canvas never has to render a half-updated frame. |
| overflow | arena-canvas (list-collection) | dismissed | Canvas is a fixed 800x600px block (D-05) — there is no scrollable/overflowing content inside it to clip, wrap, or truncate. |
| zero-one-many | arena-canvas (list-collection) | ✅ covered | 0 tanks drawn while connecting, 1 tank (local only) while waiting for opponent, 2 tanks once matched. |
| empty | tank-entities (list-collection) | ✅ covered | No tank sprite exists for a connection slot until its owning player has joined — matches arena-canvas's empty-state handling. |
| loading | tank-entities (list-collection) | ✅ covered | No tank sprites are drawn during the initial WebSocket handshake, before the first `joined` message. |
| error | tank-entities (list-collection) | ✅ covered | On disconnect, the affected tank sprite freezes at its last-known position rather than disappearing — matches arena-canvas's error handling. |
| populated | tank-entities (list-collection) | ✅ covered | Both P1 and P2 sprites render simultaneously once matched, each independently rotating per its own `facing`. |
| partial | tank-entities (list-collection) | dismissed | Each tick's tank record (`x, y, facing`) is atomic — the server never broadcasts a partially-filled tank state; partial-data rendering is not a real scenario this phase. |
| overflow | tank-entities (list-collection) | dismissed | Match is hardcoded to exactly 2 players server-side this phase (RESEARCH.md Open Question 2); no unbounded list, no scroll/overflow surface exists. |
| zero-one-many | tank-entities (list-collection) | ✅ covered | 0 tanks drawn while connecting, 1 tank (local only) while waiting for opponent, 2 tanks once matched — directly tied to the empty/loading/populated rows above; tanks are drawn, not counted in text, so no pluralized copy is needed. |
| overflow | connection-status (static-content) | ✅ covered | All status copy is fixed and developer-authored (see Copywriting Contract), kept under ~50 characters — well within the 800px canvas width at Body size, so no wrap/truncation handling is needed this phase. |
| long-text | connection-status (static-content) | ✅ covered | No user-generated or dynamic text exists this phase (no usernames/chat until Phase 4/5); every status string is a fixed, pre-authored copy row above. |
