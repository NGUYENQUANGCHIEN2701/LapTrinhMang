<objective>
Make the Java server the sole owner of tank positions: a fixed 30 Hz tick loop advances continuous positions from held-direction intent using delta-time, clamps them to the arena, and broadcasts one identical snapshot to both sessions every tick — while the connection layer accepts input intent and nothing else.

Purpose: This is where "server-authoritative" stops being a stated intention and becomes enforced code. Three things that are expensive to retrofit are settled here: input is state rather than a delta (so duplicate frames are harmless), all mutation is confined to one thread per match (so concurrent input cannot corrupt state), and the handler dispatches on `type` (so a forged frame is a no-op). Retrofitting any of these later means rewriting the protocol and the combat logic on top of it.

Output: Tanks that move on the server, positions that both clients agree on, and a test suite that proves a browser cannot lie to the server.
</objective>

Create `Direction` as an enum of exactly `UP, DOWN, LEFT, RIGHT, NONE` — four movement directions plus a rest value, per D-02. No diagonals, and no numeric angle field on the enum: the facing angle is a rendering concern that lives on the client (UI-SPEC Tank Visual Spec), not on the wire.

Extend `GameState` with a per-slot mutable tank holding `double x`, `double y`, `Direction facing`, and `Direction intent`. `setIntent(PlayerId, Direction)` overwrites `intent` — a plain assignment, deliberately last-write-wins. This is the single most important semantic in the file: because intent is current-direction STATE rather than an accumulated instruction, a duplicated, retransmitted, or out-of-order frame carrying the same direction is a no-op, and no de-duplication machinery is needed anywhere.

`advance(double dtSeconds)` iterates the occupied slots. For a slot whose intent is `NONE`, do nothing at all — the position must come out bit-identical, which is what makes "a client that sends no input stops moving" (ROADMAP success criterion 3) literally true. Otherwise set `facing = intent` and displace the position by `GameConfig.TANK_SPEED_PX_PER_SEC * dtSeconds` along that axis: UP decreases y, DOWN increases y, LEFT decreases x, RIGHT increases x. Setting facing and moving in one step is D-01 — the body's orientation and its travel direction are the same value, and there is no second angle. Then clamp x into `[0, GameConfig.ARENA_WIDTH - GameConfig.TANK_SIZE]` and y into `[0, GameConfig.ARENA_HEIGHT - GameConfig.TANK_SIZE]` so a 32px tank always stays fully inside the 800x600 arena (D-05). Increment the tick counter last.

Multiply by measured elapsed seconds, never by a constant per-tick step. A per-tick constant looks identical on a quiet local machine and silently changes the game's speed the moment tick timing jitters under load or under a debugger (PITFALLS.md Pitfall 3), and it makes the delta-time equivalence test above impossible to satisfy. Build it correctly on the first line rather than as a later fix.

Build the map fresh on every call and hand out an immutable copy — the snapshot must be a value that cannot change under a reader after it leaves the executor thread.

Add `xOf`, `yOf`, `facingOf` and `tickCount` as plain accessors so `GameStateTest` can assert on positions without reaching through the JSON layer.

`GameState` has no thread-safety machinery of its own and needs none — its sole caller is the match executor, which is set up in Task 2. Fill in `Match`'s tick loop. `start()` schedules `executor.scheduleAtFixedRate(this::tick, 0, GameConfig.TICK_INTERVAL_MS, TimeUnit.MILLISECONDS)` — 33ms, roughly 30 Hz — and guards against a second scheduling so repeated calls are harmless. Keep `lastTickNanos` as a field initialised from `System.nanoTime()`.

`tick()` measures `dt = (now - lastTickNanos) / 1_000_000_000.0`, updates `lastTickNanos`, calls `state.advance(dt)`, takes one `ServerMessage.State snapshot = state.snapshot()`, and passes that single object to `broadcast(snapshot)`. Taking one snapshot and handing the same value to both sessions is what makes "both windows show identical positions" structurally true rather than coincidentally true — there is no second code path that could compute a per-client view, so the two players cannot drift apart even in principle.

Wrap the whole body of `tick()` in a try/catch that logs and returns. `scheduleAtFixedRate` silently cancels the recurring task forever if the task throws, which presents as "the game froze for both players and the server printed nothing" — the worst possible failure mode during a live demo.

`broadcast(ServerMessage.State snapshot)` iterates the two slot sessions, skips nulls, skips any whose `isOpen()` is false, and calls `send(snapshot)` inside a per-session try/catch so a socket that closes between the check and the send cannot abort the tick for the other player.

`submitInput(PlayerId id, Direction dir)` does exactly one thing: `executor.execute(() -> state.setIntent(id, dir))`. It is called from a Jetty I/O thread, so it must never touch `state` directly. Every mutation of match state in this codebase — from the timer and from every inbound frame alike — arrives on this one executor thread, and that is the entire concurrency design. Do not reach for JDK lock primitives or concurrent collections anywhere under the match package as a belt-and-braces addition, and do not name them in comments either: a partly-locked, partly-confined design is how races survive local testing and surface only under two real simultaneous players (PITFALLS.md Pitfall 4).

Add `tickOnce(double dtSeconds)` as a deterministic test seam: submit a task to the executor that runs the same advance-and-broadcast body with a caller-supplied dt, and block on its completion. This lets `MatchBroadcastTest` assert exact values without sleeping on wall-clock timing, while still exercising the real executor.

`MatchBroadcastTest` uses a small in-test `RecordingSession implements PlayerSession` that appends every payload to a list and reports a settable open flag. No server boot, no sockets — this is a fast unit test, and the real-socket version of the same guarantee lives in plan 01-04's stress test.

Create `ClientMessage` as a record of `(String type, String direction)` annotated `@JsonIgnoreProperties(ignoreUnknown = true)`. The tolerance is deliberate: a browser can send whatever extra fields it likes, and they must be discarded silently rather than causing a deserialization failure that the handler then has to distinguish from a real error. Notice what the record does *not* have — no player id, no x, no y, no tick. A field the server cannot read is a field a browser cannot lie about, so the narrow record is itself the primary defence.

Replace the inert `onMessage` from 01-01 with the real input path, in this order:

1. Reject on length first — if the raw message exceeds `GameConfig.MAX_INBOUND_FRAME_BYTES`, increment the rejected counter and return before calling `ctx.messageAsClass`. Parsing an unbounded frame is the cheapest denial-of-service available to an unauthenticated connection this phase.
2. Resolve the sender's identity from the server's own record — `ctx.attribute("playerId")`, bound at connect time. If it is absent (a refused third connection), increment and return. The id is never read from the frame; there is no code path from a frame's contents to another slot's intent.
3. Deserialize inside a try/catch. Any exception increments the counter and returns.
4. Dispatch on `type`: anything other than the literal `"input"` increments the counter and returns without touching the match. This is the line that makes a devtools-crafted state frame a no-op (ROADMAP success criterion 3) — the server has no branch that would apply one.
5. Map the `direction` string onto the `Direction` enum, treating an unrecognised value as a rejection rather than a default. Then call `match.submitInput(playerId, direction)` and return.

Expose `rejectedMessageCount()` backed by an `AtomicLong` — this counter is written from Jetty I/O threads, which are outside the match executor's confinement, so it needs its own thread-safe primitive. It lives in the connection package, not the match package, precisely so the match core's no-locks rule stays intact.

`InputDispatchTest` drives `onMessage` directly with a fake `WsContext`-equivalent seam rather than booting a server, keeping it a fast unit test; the over-a-real-socket version of the forged-state check is plan 01-04's job. ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `GameWebSocketHandler.onMessage` | Arbitrary attacker-chosen JSON arrives here on an open socket; this is the phase's primary trust boundary. |
| Jetty I/O thread → match executor thread | Inbound frames arrive on a different thread from the one that owns `GameState`; every crossing must go through the executor. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Tampering | `GameWebSocketHandler.onMessage` — forged authoritative state | high | mitigate | `onMessage` dispatches on `type` and has no branch that applies anything but `"input"`; `ClientMessage` declares no positional or identity field, so a crafted `{"type":"state",...}` frame cannot be read even if the dispatch were bypassed. Proven by `InputDispatchTest`, which asserts unchanged coordinates rather than only a counter. |
| T-01-02 | Elevation of Privilege | player-slot binding | high | mitigate | `PlayerId` is read from `ctx.attribute("playerId")`, written by the server at connect time, and never from frame contents. A frame carrying another player's id moves only its own slot; a frame on a refused connection has no attribute and is dropped. Proven by `InputDispatchTest`. |
| T-01-03 | Denial of Service | oversized or malformed inbound frames | medium | mitigate | Length check against `GameConfig.MAX_INBOUND_FRAME_BYTES` runs before deserialization; deserialization is wrapped in try/catch; `tick()` is wrapped in try/catch so a thrown exception cannot silently cancel the recurring task and freeze the match for both players. Medium severity on the primary trust boundary → mitigated at ASVS L1. |
| T-01-04 | Repudiation | no per-action audit log of match input | low | accept | There are no accounts, no persistence and no stakes this phase (AUTH-* and LEADER-01 are Phase 4), so an audit trail has no consumer and no dispute it could settle. Revisit when Phase 4 attaches real identities to matches. |
