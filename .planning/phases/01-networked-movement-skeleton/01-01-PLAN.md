- **Decision: `promote`.** `Match` is a real instantiable object that owns its own `ScheduledExecutorService` and its own `GameState`, and `GameWebSocketHandler` receives a `Match` by constructor injection. Phase 4's "many matches" then becomes "hold a map of `Match` instances" — an additive change — instead of a rewrite of every state access.

**Server side of the round trip.** `GameConfig` holds every number from the `<interfaces>` block above — arena 800x600 per D-05, spawns (40,40) and (728,528) per D-06 (a 32px tank inset from each opposite corner), speed 150 px/sec per D-04 (Claude's discretion, tunable here and nowhere else). `Main.main` builds the app with the Javalin 7 shape only: `Javalin.create(config -> config.routes.ws("/ws", handler::register)).start(GameConfig.PORT)`. The pre-7 form of calling `.ws(...)` on an already-created `Javalin` instance does not compile against 7.2.3 and is the single most likely copy-paste mistake here, because nearly every tutorial predates the 7.0 routing change.

`Match` is an ordinary instantiable class — constructed in `Main`, handed to `GameWebSocketHandler` by constructor. It owns `private final ScheduledExecutorService executor = Executors.newSingleThreadScheduledExecutor()` and `private final GameState state = new GameState()`. Declare **no** `static` mutable field anywhere under `com/tankbattle/match/` — see the `<assumption_delta_decision>` block above for why this matters for Phase 4. `Match.join(PlayerSession)` fills slot P1 then P2 and returns the assigned `PlayerId`, or `null` when both are taken; it also calls `state.join(id)`. `Match.leave` clears the slot and calls `state.leave(id)`. `Match.start()` is idempotent — implement it and call it on first join, but leave `tick()` unimplemented/empty for now; plan 01-02 fills it in.

`GameState` for this task tracks only occupancy and the spawn positions: `join(PlayerId)`, `leave(PlayerId)`, and `snapshot()` returning a `ServerMessage.State` whose `players` map contains an entry ONLY for occupied slots (so a lone player yields a one-entry map — this is what makes the client's waiting-for-opponent state real rather than simulated).

`ServerMessage` is a final class holding the four nested records in the `<interfaces>` block. Both `Joined.type` and `State.type` are literal discriminator strings — this is the envelope every later message kind extends by adding a new `type` value, not by changing shape (RESEARCH.md Envelope discipline). Build outbound payloads exclusively from these records: never pass a `WsContext`, a session id, a remote address, a thread handle, or a live domain object to `ctx.send`.

`GameWebSocketHandler.register(WsConfig ws)` sets four callbacks. `onConnect`: call `match.join(new WsPlayerSession(ctx))`; when it returns `null`, increment `rejectedConnectionCount` and call `ctx.closeSession(1013, "match full")` without registering anything for that context; otherwise store the id with `ctx.attribute("playerId", id)` and `ctx.send(ServerMessage.joined(id))`. `onClose`: `match.leave(...)` for the session. `onError`: log and return — do not rethrow. `onMessage`: leave it as a no-op that ignores every frame for now; plan 01-02 makes it the input path, and shipping it inert means a forged frame cannot do anything even between the two plans.

**Client side of the round trip.** `client/src/game/types.ts` gets the discriminated union from `<interfaces>` verbatim. `useGameSocket(url)` opens one `WebSocket` in a `useEffect`, and in `onmessage` switches on `msg.type`: a `state` frame is written to `stateRef.current` and nothing else happens — no React state update on that path, because a tick-rate re-render is the anti-pattern this whole client architecture exists to avoid (project ARCHITECTURE.md Anti-Pattern 2). A `joined` frame does set React state (`joined`, `playerId`, `status`), which is correct: it fires once per connection, not per tick. `status` moves `connecting` → `waiting` on `joined`, → `live` once `stateRef.current.players` holds both slots, and → `lost` on `onclose`/`onerror`. Expose `sendInput` as a stub that serializes `{ type: 'input', direction }` and sends it — plan 01-03 wires the keyboard to it. Return the cleanup that closes the socket.

`statusCopy.ts` holds `STATUS_COPY`, `STATUS_COLOR` and `statusText(status, playerId)` transcribing the UI-SPEC Copywriting Contract exactly: "Connecting…", "Waiting for opponent…", "Match live — you are Player {N} ({color})." with P1 = blue and P2 = orange, and "Connection lost — check that the server is running, then refresh this page to reconnect." Colors: connecting/waiting `#a1a1aa`, live `#22c55e`, lost `#ef4444`. Every string the page displays comes from this module — no inline literals in `App.tsx`.

`App.tsx` renders the page heading "Tank Battle Online" (24px/600/1.2 per UI-SPEC Typography) and the status line (16px/400/1.5) with an 8px gap between them, on the `#18181b` page background with 16px outer padding. `index.css` sets `font-family: system-ui, sans-serif` and the background. No canvas element yet.
