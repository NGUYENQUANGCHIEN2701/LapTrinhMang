<objective>
Give the browser its half of the loop: a canvas that draws the arena and both tanks purely from the server's last broadcast, and a keyboard handler that sends direction intent on key-state changes and nothing else.

Purpose: This is the visible payoff of the phase — the point at which a human watching two windows can see the other player move. It is also where the client's permanent architectural boundary is set: rendering reads server state and never computes a position, and input emits intent and never a result. Getting that boundary right here means Phase 2's bullets and Phase 3's HP drop into the same pipeline instead of forcing a rewrite.

Output: A playable-looking arena, keyboard control, and a status line that tells the truth in all four connection states.

`drawArena(ctx)` fills the whole 800x600 surface with the arena colour and strokes a 3px frame in the frame colour around the edge. Nothing else — no grid, no texture, no walls; walls are COMBAT-05 in Phase 2 and drawing a placeholder for them now would be inventing UI for a feature that does not exist.

`drawTank(ctx, tank, playerId, isLocal)` draws one tank as a rigid unit. Save the context, translate to the tank's centre (its `x`/`y` plus half the 32px bounding box), rotate by `FACING_ANGLE[tank.facing]`, then draw in local coordinates: the 28x20 body rectangle with a 2px corner radius filled in the player's colour and stroked 2px in a 20%-darker shade of that same colour, and the 6x14 barrel in the barrel colour protruding about 10px from the body's front-centre edge. Body and barrel rotate together because they are drawn inside one transform — under D-01 the tank has no independent turret, so there is deliberately no second rotation to apply. Restore the context. Rotation snaps: apply the angle directly with no interpolation between frames, because D-02 gives exactly four facings and a tween would imply intermediate angles the protocol cannot express. When `isLocal` is true, additionally stroke a 2px ring in the own-tank colour 4px outside the bounding box, so a player can identify their own tank without having to remember which colour they were told they are. Never draw that ring for the opponent.

Derive the darker border shade programmatically from the fill colour rather than hardcoding two more hex values, so the relationship stays true if the player colours are ever retuned.

`GameCanvas.tsx` renders `<canvas width={800} height={600}>` — a fixed single-screen arena with no camera scroll, zoom or follow, per D-05. In a `useEffect`, start a `requestAnimationFrame` loop that on each frame reads `props.socket.stateRef.current`, calls `drawArena(ctx)`, then iterates the entries of `players` and calls `drawTank` for each, passing `isLocal = (id === props.socket.playerId)`. Return the cleanup that calls `cancelAnimationFrame`.

The frame loop must read the ref directly and must not go through React's re-render path. The socket hook already writes each incoming tick straight into that ref for exactly this reason: a re-render at 30 Hz is the anti-pattern this whole client architecture exists to avoid (project ARCHITECTURE.md Anti-Pattern 2). Do not introduce a React state hook in this component, and do not name one in a comment either — a source gate asserts this file is free of it.

Three rendering states fall out of this design for free, and the implementation must not accidentally break them: with `stateRef.current` still null (handshake in flight) the loop draws the arena and no tanks; with a one-entry `players` map (waiting for an opponent) it draws exactly one tank and leaves the opponent's corner empty with no placeholder; and when the socket closes, the ref simply stops being updated, so the loop keeps redrawing the last received state and the picture freezes in place rather than clearing. Freezing is the specified behaviour, not a bug — it keeps the last moment visible for context while the status line explains what happened.

`KEY_TO_DIRECTION` maps both control schemes onto the four directions: `ArrowUp`/`w`/`W` to UP, `ArrowDown`/`s`/`S` to DOWN, `ArrowLeft`/`a`/`A` to LEFT, `ArrowRight`/`d`/`D` to RIGHT. Four directions only — there is no diagonal entry and no combination rule that could produce one, per D-02.

`resolveDirection(heldKeys)` is a pure function over the ordered list of currently-held keys: it returns the direction of the most recently pressed key still held, or `'NONE'` when the list is empty. Last-pressed-wins is what makes a player who rolls from one arrow onto another get an immediate turn instead of staying stuck on the first key until they release it. Keeping this pure and exported means the whole non-DOM half of input handling is testable in isolation the moment a client test runner is added.

`attachInput(onDirectionChange)` registers `keydown` and `keyup` listeners on `window`, maintains the held-key list, and returns a detach function that removes both listeners. Two rules govern when it calls back:

- Ignore any `keydown` whose `repeat` flag is set. The browser fires auto-repeat `keydown` events for a held key many times per second; acting on them would put one WebSocket frame on the wire per repeat event.
- Call `onDirectionChange` only when `resolveDirection` returns something different from the last value already reported. This is the edge trigger: holding a key for five seconds sends exactly one frame at press and one at release, not three hundred. It is also what makes the server-side idempotency guarantee (input is current-direction state, not a delta) matter in practice rather than in theory — the two halves are designed to fit.

Also call `event.preventDefault()` for keys in the map, so arrow keys scroll the tank and not the page.

Wire it in `GameCanvas.tsx`: a `useEffect` that calls `attachInput(props.socket.sendInput)` and returns its detach function. Confirm `sendInput` in `useGameSocket.ts` serialises exactly `{ type: 'input', direction }` and sends it only when the socket's `readyState` is open — a send on a socket that is still connecting or already closed throws and would take down the keydown handler with it.

The tank must not move on screen until the server's next broadcast comes back. There is no local position update anywhere on this path: the client sends intent, and the picture changes only when the authoritative answer arrives. On a local network that round trip is invisible to the eye; under the artificial latency the README's UAT recipe asks for, it is visible and correct.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Javalin `/ws` → browser render path | Server-sent JSON is parsed and drawn by the client; the client must treat it as data to render, never as code or markup. |
| keyboard → outbound WebSocket frame | The only thing the client is permitted to put on the wire is direction intent. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-01-08 | Tampering | `GameCanvas.tsx` render path | medium | mitigate | The frame loop draws only from `socket.stateRef.current`, which is written solely by the socket's message handler; there is no client-side position computation and no code path by which a local value could reach the wire or another player's view. `sendInput` serialises a fixed two-field object and can emit nothing else. Asserted by the `stateRef.current` and `sendInput` source gates above. |
