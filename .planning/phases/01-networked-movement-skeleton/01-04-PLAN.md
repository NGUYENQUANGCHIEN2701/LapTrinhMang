<objective>
Prove the two phase guarantees that only show up under real conditions: that two players hammering movement keys at genuinely the same time cannot make the server disagree with itself, and that a browser cannot talk its way into changing the game state.

Purpose: These are ROADMAP success criteria 3 and 4, and both belong to the class of bug that never reproduces in single-client development and surfaces during a live demo. The concurrency confinement built in plan 01-02 is a claim until something actually races it; the server-authority dispatch is a claim until something actually forges a frame over a real socket. This plan converts both claims into standing regression tests, and writes down the manual acceptance recipe so the phase's evidence is reproducible rather than anecdotal.

Output: Two integration tests that run on every commit, and a README acceptance section a grader can follow.
</objective>

  <action>
Write the test RESEARCH.md specifies as the primary, repeatable verification of success criterion 4.

Boot the real application — the same `Javalin.create(...)` wiring `Main` uses, on an ephemeral port — in `@BeforeEach`, and shut it down in `@AfterEach`. Open two real `jetty-websocket-jetty-client` connections so the frames travel over an actual socket through Jetty's framing, not through an in-process shortcut. Each client keeps its own recording of every received frame, storing the parsed `tick` number against the raw text of that frame.

Drive both clients from two separate threads for about three seconds. Each thread cycles rapidly through the four directions — a few milliseconds apart, far faster than a human and far faster than the 33ms tick — so that input from both players genuinely interleaves with each other and with the tick task. Sending at a slower cadence than the tick rate would let each frame land in its own quiet tick and would defeat the entire point of the test. Use a latch or a joined thread pair so the burst ends deterministically rather than on a sleep in the assertion path.

Then assert four things:

1. **No exception anywhere.** Neither client thread recorded a throwable, and neither socket closed with an error status. Record throwables into a collection from inside the threads and assert it is empty, rather than relying on the test method's own stack — an exception on a client thread otherwise vanishes silently and the test passes green while proving nothing.
2. **No drift.** For every tick number that appears in both recordings, the two recorded frame texts are equal. This is the direct check that both players were shown the same world: if a race let the two broadcasts be computed from different intermediate state, the payloads for one tick number differ and this assertion fails. Assert that the overlap set is non-empty first, so an empty intersection cannot pass vacuously.
3. **In bounds.** Every position in every recorded frame satisfies `0 <= x <= 768` and `0 <= y <= 568`. A race that let two writes interleave inside `advance` would most visibly present as a position outside the arena.
4. **Still ticking.** The last tick number is strictly greater than the first, by at least the number of ticks three seconds should produce with generous slack. This catches the failure mode where an exception inside the scheduled task silently cancels the recurring task forever: the game freezes for both players, no error surfaces, and every other assertion above would still pass on the frames captured before the freeze.

Give the test method a generous JUnit timeout so a hang fails the build rather than stalling it. If Surefire needs configuration to accommodate a multi-second test, add it in `server/pom.xml`; do not shorten the burst to fit a default, because a burst too short to interleave is a test that proves nothing.
  </action>

`InputDispatchTest` already proves the handler drops a forged frame when called directly. This task proves the same thing survives the full path a real cheat would take — through a browser's socket, Jetty's framing, Jackson's deserialization and the live tick loop — because that is the path ROADMAP success criterion 3 is actually worded about.

`ForgedStateRejectionTest` boots the real server on an ephemeral port and connects two real clients. Client 1 sends a legitimate input frame and both clients confirm the tank starts moving, establishing that the socket is genuinely live. Client 1 then sends a crafted frame claiming an authoritative position far across the arena — the same shape the server itself broadcasts, with a plausible tick number and both players' coordinates filled in. Assert that in the frames both clients receive afterwards, the coordinates continue on exactly the trajectory the tick loop was already producing, with no jump toward the forged values, and that `rejectedMessageCount()` increased by exactly one. Assert on the coordinates and not only on the counter: a counter-only assertion would pass even if the frame had been counted and also applied.

Then send a frame of a type that does not exist in the protocol at all, and one that is well-formed input but names a direction outside the four, and confirm each is counted and changes nothing. Together these cover the whole rejection surface as a browser would reach it.

Extend `README.md` with an **Acceptance check** section giving the reproducible manual recipe, transcribed from 01-VALIDATION.md's Manual-Only Verifications row:

1. Start both processes. Open the client in two genuinely independent browser processes — a normal window plus an incognito or second-profile window, or two machines on the same network. State plainly that two tabs of one browser is not a valid check: tabs share storage and, more importantly, share a process and a network path, so the timing conditions the concurrency work exists to survive never arise.
2. In one window, open DevTools and apply network throttling (a Slow 3G-style profile, or a custom profile with a few hundred milliseconds of added latency). Localhost has effectively zero latency, so without throttling the lag-related behaviour of the design is simply never exercised.
3. Both players hold and mash movement keys simultaneously for a sustained stretch — thirty seconds or so. Confirm both windows show the tanks in the same places throughout, that neither freezes, and that the server terminal prints no exception.
4. Confirm a client that stops sending input stops moving while the other keeps going.
5. In one window's DevTools console, grab the open WebSocket and send a crafted state frame claiming a teleport. Confirm the other window's view is completely unaffected and your own tank snaps back to wherever the server says it is on the very next broadcast. Include the exact console snippet so this is a copy-paste check rather than an exercise.

Cross-reference the automated tests next to the manual steps, so a reader can see which guarantees are already enforced on every commit and which need the human in the loop.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → live `/ws` socket under load | The realistic attack and failure surface: arbitrary frames arriving concurrently with the tick task on a live connection. |
| Jetty I/O threads → match executor thread | Two independent I/O threads plus the scheduled tick task all reach the same `GameState`; only the executor may serialize them. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-10 | Tampering | concurrent mutation of `GameState` from multiple Jetty I/O threads | high | mitigate | Every write reaches `GameState` only through `Match`'s single-threaded scheduled executor, and no lock primitives or concurrent collections are mixed into the match package. `ConcurrentInputStressTest` proves this under genuine concurrent load over real sockets: identical payloads per tick across both clients, positions in bounds, no throwable on either client thread, and a tick counter still advancing at the end. This is the standing regression guard for PITFALLS.md Pitfall 4, the failure mode that never reproduces in single-client development. |
| T-01-01 (re-verified end-to-end) | Tampering | forged authoritative frame over a live socket | high | mitigate | `ForgedStateRejectionTest` drives the full browser path — real socket, Jetty framing, Jackson deserialization, live tick loop — and asserts the broadcast trajectory is unchanged after a crafted state frame, plus a matching increment in `rejectedMessageCount()`. Complements the unit-level `InputDispatchTest` from plan 01-02 rather than replacing it. |
</threat_model>
